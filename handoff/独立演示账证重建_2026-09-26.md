## 实现

- `apps/api/tools/demo-seed.mjs` 增加 `--catalog-only`，仅造门店、服务、顾客、套餐、账号等配置；不再为新生成器插入没有结算凭证的财务/储值/预约流水。原有 legacy 行为未暗改，但文件明确不应再用于财务验收。
- `apps/api/tools/consistent-demo.mjs` 只接受显式的新空目录与独立端口，拒绝现有数据库重建；已完成目录重跑只读对账。
- `apps/api/tools/demo-clock.mjs` 仅在生成器的子进程通过 `--import` 使用；要求 loopback、新库 building marker、sandbox-data 目录且非生产环境。生产应用从不引用它。
- 历史各时刻顺序调用真实业务 API：演示身份登录/绑定 → 充值 → 即时开单 → 模拟签署 → 日结；支付腿、收入、耗卡、签署快照一起生成。没有事后修改签署日期或快照。
- 每张预约和结算携带 `demo_seed=consistent-demo-v1`，顾客名称含“演示”，签名文字为“演示模拟签署（非真人授权）”。笔迹仅为演示方框，绝非任何人的真实签名。
- 正常运行不加载时钟，使用当前真实时间；不会自动平移历史记录。

## 限制与后续

- 本批核验的是 API 与 SQLite 账证，未把同一演示的每个页面重新做视觉验收，也未将开发者工具切换到 4368。
- 该演示基准日为 2026-09-26；没有硬造当天营业收入。用户当日没有服务时 0 是正确状态，可以查看 9 月 25 日或本月。
- 非交易目录沿用既有种子。没有给每个积分奖品造兑换记录，也没有复制真实作品照片；目录有套餐/优惠券模板，不声称每个子功能都已灌满。
- 生成过程额外发现即时结算的 `publicCode()` 在集中创建时可能撞唯一键；工具只在后端事务回滚且明确报该唯一键冲突时等待后重试，未掩盖其他错误。业务端编号应另加重试或改更宽随机编号，交父任务处理。
