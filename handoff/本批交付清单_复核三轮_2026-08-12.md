## 一、D39(🔴 换店串店)——数据随店走

**根因三件叠加**:①顾客 token 按「出生店」的用户行签发(会员=用户×店,同一微信身份每店独立档案),换店后旧 token 把上家身份带进本店——头部字段全是上家的,而 /my/* 明细按新店查=全空(店主看到的「积分明细又是空」);②`ensureLogin` 只查过期不查租户;③`lucky_member` 快照换店不清。

**修复**:
- auth 打租户戳;租户不匹配=对本店而言未登录 → `wx.login` **静默重登**为本店身份(顾客无感);重登失败如实清会话,绝不拿上家身份凑数。`refreshMember`/`myBalance` 请求前自愈。
- **L2(换店残留机制,第 2 案后清单化)**:全仓 storage 键 12 个逐个裁定——

| 键 | 裁定 |
|---|---|
| lucky_mini_auth | 打租户戳,不匹配自动重登(本批) |
| lucky_member / lucky_store_currency / lucky_store_deposit / lucky_store_ai / lucky_cart / lucky_orders / lucky_style_preset | **换店清**,统一走 `api.onStoreSwitched()`(本批;币种=第 1 案已修,并入) |
| lucky_store_id::<tenant> | 键自带租户,不清 |
| lucky_lang / lucky_service_type / lucky_demo_mode | 用户偏好/通用值,不清 |
| lucky_admin_* / lucky_finance_key / lucky_merchant_ai / lucky_quote_draft | 商家端,无换店流(跨店有 D35 闸),不清 |

- 换店入口两个(选店页 applyTenant + app.js 扫码/深链 resolveTenant)同一清场出口;深链只在租户实际变化时清。
- **L5 实点**:选店页真点店行,双向往返 5/5,me 页四字段(累计消费/积分/称谓/余额)≡ 当前店后端真相:jics 198/368/会员/5 ↔ lucky 564/1200/Gold Member/864。截图 d39-jics/d39-lucky。
