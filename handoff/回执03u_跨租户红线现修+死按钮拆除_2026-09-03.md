## 一、红线三件

### 1. 堵口 —— 但要先更正我自己在 02b⑤ 的说法

我写的是「建单不校验顾客属于本租户」,**只说对了一半**:

| 路径 | 实况 |
|---|---|
| `/admin/bookings/direct`(商家侧) | **本来就有** `USER_TENANT_MISMATCH` 闸(`local-server:15042`) |
| `POST /bookings`(顾客侧) | `userId` 强制取自会话;微信登录按 `openid + tenant_id` 找档、找不到就在这店新建 |
| 那 5 行怎么来的 | **夹具脚本直接写库**(notes:`O7 walk fixture,验后撤` × 4 · `D2D3现场·已签署` × 1) |

**所以真正演示出来的泄露在读口**:不管脏行怎么进来,`serializeBooking` 拼 user 对象时
`WHERE id = ?` **不比对租户**,照发不误。归族「读写两道闸律」第五案 —— 这次是**读口**那一侧没收。

两道闸都落了:

- **读口(真正堵住已演示泄露的那道)**:按 `users.tenant_id = bookings.tenant_id` 连;
  连不上**不下发 user 对象**,只留 user_id。「宁可少给,不许给别人家的」。
- **写口(纵深防御)**:`createBooking` 取顾客加 `AND tenant_id = ?`,
  比的是**这张单要写进去的那个租户**(`input.tenantId`),不是 `currentTenantId()` ——
  顾客侧路由把 `resolveTenant()` 放进 `body.tenantId`,两者未必相同,
  **拿错对象去比,闸看着在守、守的却是别的东西**。

### 🔴 堵口顺带扒出一个更深的东西(回归当场咬出来的)

我堵完口跑回归,「默认配置下顾客下单成功」**红了**。查下去是这个:

```sql
tenant_id TEXT NOT NULL DEFAULT 'lucky-luxe'
```

`registerEmailUser`(演示邮箱登录那条老路)**不写这一列** ——
于是每个走邮箱注册的顾客都**静默落进旗舰店**,再去别家店下单,
就生成一行「单属 B / 人属 A」的串味数据。**那 5 行的同一个形状,机制就在这儿。**
归族「静默失败器族」:**一个默认值让「没填」看起来像「填对了」**。

**没有改夹具让它绿**,改的是产品:

1. 注册在哪家店就建在哪家店(注册口传 `resolveTenant`,落库写 `tenant_id`);
2. 同一邮箱在不同店是**不同档案**(按 `email + tenant_id` 找,与微信登录同口径);
3. 下单时取**这个人在当前这家店**的档案 —— 新出口 `profileIdInTenant`,
   规则照微信登录那套:先按店找(openid → email → 本人 id),找不到就在这店建一份。
   微信路径下第一步必然命中(登录时已建),**不会多建**;只有邮箱老路走到建档那一支。

闸本身也修正过一次:严格相等会把「**还没归属**」也拒掉。
**「还没归属」和「属于别家」是两个状态,不许说同一句话** —— 闸只拒后者。
(两库真实数据里无归属用户 **0/273** 与 **0/186**,这条兜底只服务演示登录;
上线前移除演示登录时,它应当一并删掉。)
