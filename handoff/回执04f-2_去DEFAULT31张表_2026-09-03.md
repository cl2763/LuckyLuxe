## 一、做法

SQLite 没有 `DROP DEFAULT`,只能重建表:**新表建 → 复制 → 删旧 → 改名 → 重建索引**,全程一个事务。

核心在 `apps/api/tenant-default-drop.mjs`(**唯一出口**),两个调用方共用:

| 调用方 | 干什么 |
|---|---|
| **开机迁移**(`local-server.mjs`) | 老库跟着部署自动去掉;没有待处置的表时是彻底的空操作 |
| `tools/drop-tenant-default.mjs` | 彩排 / 应急手跑:`requireTarget` · 默认 dry-run · `--apply` · 先备份 · **四栏前后对照** |

**建表语句同批改掉 23 处** —— 只迁移老库不改建表语句的话,**新库照样带 DEFAULT**,判据也翻不过来。

### 🔴 两个坑,都是彩排撞出来的

1. **`DROP TABLE bookings` 会报 `error in trigger payments_tenant_fill: no such table: main.bookings`**
   —— **别的表上的触发器引用了正在被重建的表**。所以不是「只摘这张表的触发器」,
   得把**全库 19 条触发器先摘下来,重建完原样装回**(账本那 12 条也在内)。
2. **我的正则把 `ALTER TABLE … ADD COLUMN` 也剥了** —— 那种语句在**非空老表上没有默认值直接失败**。
   ALTER 那两处已还原并写明理由:它们的 DEFAULT 只用来给存量行落值,随后由重建再摘掉,**两步是配套的**。

`Error: NOT NULL constraint failed: stores.tenant_id`。**不再静默落进旗舰店。**

### 🔴 换锚之后多咬出一族

D131 原来按「带 DEFAULT 的表」找清单 —— 默认值去掉后这个锚会得到 **0 张,判据会绿在空气上**。
换成按「**有没有 `tenant_id` 列**」取,才看见另一族:
`payments` / `business_hours` / `booking_slots` / `booking_status_history` /
`technician_schedules` / `store_special_dates` / `booking_drafts` —— 它们的 `tenant_id` 是
ALTER 加的**可空**列,漏写不报错、**会落 NULL**,靠 `<表>_tenant_fill` 从父行补。

所以这一族的判据不是「INSERT 必须写」,而是「**必须真有那个触发器**」——
新加一张这样的表却忘了配触发器,行就带着 NULL 租户躺进库里。

**顺带咬出一条**:`finance_targets` 的 `tenant_id` 可空**且没有** `_tenant_fill` 触发器。
现查:全仓两处 INSERT(`local-server.mjs:14195` / `:14487`)**都显式写了** tenant_id;
本机库 4 行、沙箱 2 行,NULL 的 **0 行**。**先进白名单(带理由与证据),不现修** ——
再多一个写入口、或出现 NULL 行,就该给它配触发器。请您裁要不要现在补上。

### 🔴 一条金丝雀的含义变了,值得记

`test-identity-tenant` ⑥b 原来是「历史坏版必须造出错标」。去掉默认值之后,
**那条 SQL 连错标行都造不出来了** —— 但它也**不报错**:`INSERT OR IGNORE` 把 NOT NULL 违规
**一起吞了**,结果是「静默不落行」。

所以去 DEFAULT 把「悄悄落错店」换成了「悄悄不落行」——
对这条回填是好事(**宁可没有,不要错的**),但 **`INSERT OR IGNORE` 这类写法本身仍是静默失败器**,
新写的时候要想到。判据已按真实机制重写,并给 ⑥ 补了反向守
(**现版回填必须真的插进去了 20 行** —— 一个「什么都不插」的回填也能让错标为 0)。
