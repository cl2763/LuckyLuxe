## 二、存在哪:同一张表,同一套字段(两端共用,零分叉)

| | 值 |
|---|---|
| 表 | **`bookings`**(不是独立的图片表) |
| 字段 | `work_images_json`(上传的)· `approved_work_images_json`(审核发布的)· `gallery_status` · `gallery_locked_at` |
| 存储形态 | **内联**在 SQLite 里:`data:image/...;base64,...` 或 `http(s)://` URL 的 JSON 数组。**不走对象存储** —— COS 目前只用于签署快照(`cosUploadAllowed()`),作品图没接 |
| 上限 | **6 张**,后端 `normalizeWorkImages()` 硬 `slice(0, 6)`;两端 UI 也都写 6 |
| 锁定 | 一旦 `gallery_status='approved'`,再传/再改一律 **409 `GALLERY_LOCKED`** |
| 写入口 | 两端**同两条路由**,没有第二套 |

**双端同源已核实**:小程序 `gallery/index.js:76` 与网页 `admin.js` 的 `data-work-image-input`
打的是**同一条** `PATCH /admin/bookings/:id/work-images`;发布同理。
**网页端没有第二张表、也没有第二条路由。**

唯一的差别是**入口摆在哪**(不是数据分叉):
小程序在「作品」tab 按单卡片上传 + 发布;网页上传在订单详情、发布在 AI 图库。

## 五、🔴 真正的问题不在上传口,在**顾客能看到哪些图** —— 两端口径不一样

这条是查的过程中撞出来的,属你分类里的**「两处真相」同族**:

| 端 | 顾客在自己订单里看到的 | 判据 |
|---|---|---|
| **网页顾客端** | **只有已发布的**。`customerVisibleWorkImages()` 第一行就是 `if (order.galleryStatus !== 'approved') return []` | `apps/web/customer.js:490` |
| **小程序顾客端** | **未审核的也看得到**。映射层写的是 `approvedWorkImages \|\| workImages`,页面再按"已完成就显示"渲染,**`galleryStatus` 拿到了却没用** | `miniprogram/utils/api.js:347` + `pages/order-detail/index.js:50` |

两件事叠在一起:

1. **`a || b` 回落** —— 已发布的没有就拿**未发布的**顶上。这正是《假数回落红线》第 1 条点名禁止的写法
   (「`a || b`、`x ? x : y`、拿另一个语义的字段顶上,全部禁止」)。
2. **同一个"已发布"闸,在两端管的范围不一样** —— 网页认它,小程序不认。

影响面(如实说,不夸大):看到的人是**顾客本人**、看的是**她自己那一单的照片**,
**不存在泄露给第三方**。但 ①它让 `approved` 这道闸在小程序上形同虚设
(技师"还没想好要不要发"的图,顾客那边已经看见了);②两端不一致 = 你一路在杀的那种病。

**这条我没改** —— 按你的规矩:改法会动"顾客能看见什么"的口径,先报你裁。
两种改法各一句:
- **A(收紧,与网页对齐)**:小程序也只显示 `approved` 的 → 一致、闸生效;代价是顾客要等技师发布才看得到自己的图。
- **B(放宽,与小程序对齐)**:网页也显示未审核的 → 一致;但 `approved` 就只剩"要不要进对外橱窗"这一个含义。

我倾向 **A**,理由是 `approved` 这道闸本来就是为"给不给外人看"设的,而顾客看自己的图**应该另开一个口径**
(比如"完成即可见自己的图,但不进对外橱窗")—— 那是第三种改法,要新口径,得你拍。
