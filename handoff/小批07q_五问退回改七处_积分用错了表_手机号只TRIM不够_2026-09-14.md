## 一 🔴 五问退回 —— 七处,逐条改

### ① 问 2 的 NULL 陷阱 —— **加不起来**

```sql
SUM(CASE WHEN (...) AND is_migrated <> 1 THEN 1 ELSE 0 END) AS 没号且非导入
```

**`is_migrated` 为 NULL 时,`NULL <> 1` 求值为 NULL,不是 TRUE** → 那一行**两个分类都不计入**。
结果:**「没号且是导入的」+「没号且非导入」< 「没有手机号」** —— **底数不闭合(J-48)。**

你说「本机库跑通了」—— **跑通不等于分类完整**,本机库很可能 `is_migrated` 全都非 NULL,而生产库未必。

**改**:
```sql
SUM(CASE WHEN (phone为空) AND is_migrated = 1 THEN 1 ELSE 0 END)                          AS 没号_导入,
SUM(CASE WHEN (phone为空) AND (is_migrated IS NULL OR is_migrated <> 1) THEN 1 ELSE 0 END) AS 没号_非导入或未知,
SUM(CASE WHEN is_migrated IS NULL THEN 1 ELSE 0 END)                                      AS is_migrated为空的行数
```
**并在回执里现算一次:两个分类相加 = 没有手机号。** 加不起来就是查询还有洞。

### ② 🔴 问 5 的积分列**用错了表** —— 而且是你自己上一段刚查清的

你在 §五 查清了:

> 「积分『挣』出来的部分是**从结算单推导的**(`SUM(subtotal_cents/100)`),**`points_transactions` 只记兑换与调整**。」

**然后问 5 里写的是 `SUM(points_transactions.amount)`。**

后果:**一个从来没兑换过的老顾客,她挣的积分全在结算单里,这条查询会把她数成「积分 0」** —— 而她正是最典型的老顾客。

**这是 J-55 的形状:新证据推翻了旧假设,但产出物没跟着改。** 而且这次「旧假设」和「新证据」隔了不到一个小时。

**改**:积分按你自己查清的口径算 —— **签署过的结算单推出的赚分 + `points_transactions` 的台账行**,两部分相加。

### ③ 🔴 手机号只 `TRIM` 不够 —— **这可能是最大的一类,而且正好打在加拿大店**

`TRIM(phone)` 只去首尾空白。**真实数据里同一个号会有多种写法**:

```
+1 416-555-1234   (416) 555-1234   4165551234   1-416-555-1234
```

**`lucky-luxe` 是加拿大店**,老顾客名单很可能是几年里不同人、不同时候录进去的。

**两个后果叠在一起**:

- **产品侧**:严格认人第二条是「号**完全一致**」→ 格式不同 = 认不出来 → **变新人。**
- **查询侧**:这条 SQL 按字面比 → **数不出来** → **报 0。**

**也就是说:如果这是真问题,你这条查询恰好会告诉我们「没问题」。**

**这是 D191 的第四种形态:号有,但格式不一致。**

**改**:问 1 和问 4/问 5 里的「同号」判断,**三档并排报**:

| 档 | 怎么比 |
|---|---|
| 字面 | `TRIM(phone)`(你现在这档,留着) |
| **去符号** | 只留数字:`REPLACE` 掉 空格 `-` `(` `)` `+` |
| **后十位**(只对 `lucky-luxe`) | 去符号后取末 10 位 |

**三档的差值,就是「格式不一致导致认不出来」的人数。** 我要看那个差。

### ④ 问 3 要按 `status` 分布

只给一个 `COUNT(*)`,**对不上账的时候不知道差在哪**(1,242 那个数含不含已取消?含不含 no-show?)。
**改**:总数 + 按 `status` 的分组计数。

### ⑤ 缺第 0 条「这一跑连的是哪份数据」(J-38)

五条之前先跑一条指纹:

```sql
SELECT datetime('now') AS 读数时刻,
       (SELECT COUNT(*) FROM users)    AS users总行,
       (SELECT COUNT(*) FROM bookings) AS bookings总行;
```

**没有这一条,后面五个数就没有「什么时候、对哪份数据」量的。**

### ⑥ 余额为负的要单列(只报)

问 4 是 `WHERE 余额分 > 0`。**余额为负的顾客**(超扣、退款异常)也是有账要算的人。
**改**:加一列「余额 < 0 的顾客数 + 合计分」,**只报,不做别的。**

### ⑦ ⚠️ WAL + `-readonly` 可能打不开 —— **打不开就停**

这个仓的库是 WAL 模式(所以备份才用 `VACUUM INTO` 而不是 `cp`)。
**WAL 库用 `-readonly` 打开,若 `-shm` 文件不存在且不能创建,会失败。**

**这不是安全问题,是「可能跑不起来」。** 但它有一个危险的诱惑:

> **打不开 → 顺手去掉 `-readonly` → 那一刻所有护栏都没了。**

**写死**:`-readonly` 打不开 → **停下来问**。
**不许去掉 `-readonly`,不许改库的 journal 模式,不许创建任何文件。**
