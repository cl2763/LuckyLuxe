### 模型定死(三句话,以后所有人照这个说)
1. **人跟微信走** —— 同一个微信在几家店都是同一个人,不许变成两个陌生人
2. **档案跟店走** —— 她在小婕店和在旗舰店,是两份独立档案
3. 🔴 **钱跟店走** —— 储值 / 积分 / 券,**充在哪店只能在哪店花**

**这三句以后不许再被「简化」成两句。** 第 1 句和第 3 句听起来矛盾,**但它们说的是两件事:身份是一个,账是分开的。**

## 一 🔴 店主说「这是最严重的」——所以要一次**跨店隔离总验**

她的原话:「**一定要确保租户不要篡位,会员档案不要串味,这是最严重的。**」

**D207 那 51 行治的是历史脏数据;这一条要的是「今天的代码会不会再串一次」。**

**做一套 `test-cross-tenant-isolation`,一个人在两家店,逐项验:**

| 验什么 | 阳性对照(必须造得出来) |
|---|---|
| 同一个微信扫 A 店码 → 建 A 店档案;扫 B 店码 → 建 B 店档案 | 两份档案的 `user_id` **不同**,而身份行能认出是同一个人 |
| A 店档案里的手机号 / 小记 / 标签 | **B 店查不到** |
| A 店储值余额 | **B 店查询 = 0,B 店消费不许扣 A 店的钱** |
| A 店积分 / 券 | 同上 |
| A 店订单 / 结算单 / 签署文件 | **B 店列表里不出现,直接拿 id 请求 → 拒** |
| 🔴 拿 A 店的登录态去打 B 店的口 | **一律拒**(不是「查不到」,是**拒**) |

🔴 **每一条都要有阳性对照**:先证明「同店能拿到」,再证明「跨店拿不到」——
**否则「拿不到」可能只是这条路本来就不通(J-58①)。**

**这一套做完,进回归,进推前清单。** 它是这个产品最贵的一条护栏。

## 三 门店码:你们早就设计好了,只是没接真码

我现查到:
```
local-server.mjs:12907   shopEntry: { scene: `t=${id}`, note: '小程序发布后可用此 scene 生成该店专属小程序码。' }
local-server.mjs:15273   注释:上线换 wxacode 真码;发版清单「码对应到具体对象」项含绑定码→档案
```
🟢 **方案是对的(scene 带店号),缺的只是接微信那个生成接口。**

**要你出一份实现计划(只列不做),写清这几件:**
1. **用哪个接口** —— 🔴 **门店码要长期贴在店里,所以必须是「不限数量」那一类**;按名额有限的那一类做,开到第几家店就没了。**把三种码的区别和名额限制量清楚写进计划。**
2. **码里带什么** —— `scene` 现在是 `t=<tenantId>`;**够不够?**要不要带「哪个技师/哪张桌」?**先只做店,别一次做到台。**
3. **扫码之后发生什么** —— 顾客第一次扫:落到这家店的首页 + **把这家店记成他的当前店**;已经是这家店的顾客:直接进
4. 🔴 **扫了 B 店的码,会不会把他在 A 店的档案带过去** —— **这一条接 §一 的总验,必须有阳性对照**
5. **码存在哪 / 怎么给店主** —— 商家后台一个「下载我的门店码」按钮,**PNG + 印刷用的尺寸**
6. **换店名/换 logo 之后,旧码还能不能用** —— 🔴 **这一条要明写**(店主上次问过二维码会不会因为换头像失效,同族)
