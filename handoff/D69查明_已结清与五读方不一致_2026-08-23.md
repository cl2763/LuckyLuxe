# D69 查明 · 「已结清 CAD $198」与积分/累计消费不一致(只查不修)

> 现场:沙箱 4310(ll-b5),店主实测账号 **演示2-矩阵8·全有**(`tmx-mx8`)。
> 结论先行:**积分没接上 = 不成立**;真缺陷只有一处 —— **订单卡在"没有签署单"时用预约底价冒充「已结清」**(假数回落,D17 家族)。夹具不完整 = 成立。

## (a) 这两单到底有没有签署单 —— 没有

| 预约 | 状态 | 预约服务底价 | 已签署结算单 |
|---|---|---|---|
| LLD76159191913 | COMPLETED | CAD $168 | **无** |
| LLD76159202195 | COMPLETED | CAD $198 | **无** |
| LLD76159213625 | CONFIRMED | CAD $168 | 无(未完成,正常) |

该客**全库 0 张签署单**、积分台账 0 行。

**那卡片上的「已结清 CAD $198」哪来的?** → 小程序订单列表的**回落分支**:
`miniprogram/pages/orders/index.wxml:41`
```
<view class="price" wx:elif="{{item.status === 'completed'}}">已结清 {{cur.p}}{{cur.s}}{{item.servicePrice}}</view>
```
没有结算单时,拿**预约上的服务底价**(198)显示成「已结清」。系统认为这单没消费,卡片却告诉顾客"结清了 198"。

## (b) 五读方各自的基数与来源(核对结果:除订单卡外,其余都自洽)

| 读方 | 现值 | 来源 | 判定 |
|---|---|---|---|
| 订单卡「已结清 ¥X」 | $198 | **无签署单时回落预约底价**(上面那行) | ❌ **撒谎的就是它** |
| 累计消费 | $0 | `customerSignedSubtotalCents` = Σ已签署单**档位小计** | ✅ 无签署单=0,自洽 |
| 会员成长值 | 0 | 同上基数(累计消费推导) | ✅ 自洽 |
| 积分 | 0 | `pointsEarnRows` = 已签署单逐张推导(见 c) | ✅ 自洽 |
| 到店次数 | **2** | 裁A `visitDaysCount` = 已签署组 ∪ 已完成预约日 | ✅ 自洽(店主看到网页"0 次"是走查时注入测试身份的副作用,不是产品值) |

> 注:「已结清」(=Σoffline 现金腿,C5 拍板)与「累计消费」(=档位小计)本就是两个事实,有签署单时也可能不等(储值抵扣时现金<小计)——这不算不一致,口径文档已写明。

## (c) 积分到底在哪一步入账 —— 它是**推导**,不是"发放函数"

- `points_transactions` 台账**只有两类写方**:`redeem`(兑换)与 `adjust`(冲正/钳位),全仓扫描确认无 earn 写方;
- **赚分=实时推导**:`pointsEarnRows()` 直接从 `settlements WHERE status='signed'` 逐张算(1 元=1 分,基数=档位小计),`pointsBalance = 推导赚分 + 台账`;
- 这是 D36 定的口径(「列表必须能加总出余额」),**不是漏接**。所以「没看到发放函数」属实,但结论相反:签署那一刻积分就算数了,只是这两单没有签署单。

## 病灶同病面(机械扫描)

全库 COMPLETED 预约 27 张:**有签署单 20 张,无签署单 7 张**,分布:
`Lucky Member ×2、演示2-测试F ×2、演示2-矩阵7 ×1、演示2-矩阵8 ×2`。
来源查明:`seedDemoBookingsForUser()` 造演示订单时**只建预约不建签署单**(`mk(nail, …, 'COMPLETED')` / `mk(lash, …, 'COMPLETED')`),所以所有走过演示种子的档案都带这个形态。
**网页顾客端无此病**(无签署单时显示「已付定金 ¥X」,不说"已结清")——四之九:病在小程序单侧。

## 顺带查出的**第三例同族**(不在店主报的三问里,已当场修)

店主那张矩阵8 截图里,黑卡还有一格在撒谎:**「卡包 0」而卡包页实有 4 张(1 次卡 + 3 券)**。
根因同族:后端 `serializeUser` 下发的 `couponCount` **写死为 0**,双端却把它当作"角标还没拿到时"的回落值显示。
这一处不改业务口径、只是删假数,已在本批修完(双端 + 两个后端 + 5 条常驻断言),详见
`handoff/本批交付清单_批③次段_卡包与商城_2026-08-23.md` 追加段。

**归纳(给 Cowork 定修法时用)**:D66 → D69 三例是同一个病 ——
**「读方拿不到真值时,拿另一个字段/另一个基数顶上,顶上的那个恒假或口径不同」**。
护栏应当是一条通则而不是逐点修:**顾客可见的数字,拿不到就显示「—」或不显示,一律不许回落到别的字段。**

## 建议修法(**未动手,等 Cowork 核**)

1. **修产品(主刀)**:订单卡的金额行**一律用后端句**(`listAmountText`,`customerOrderBadges` 已唯一持有);**没有签署单就不许出现「已结清」**——空串时前端不回落底价,按已完成单显示「本单未产生结算单」(与详情页 A3 同句族)。同族回落全仓扫尽(`item.servicePrice` 冒充金额的其他位置一并清)。
2. **修夹具**:`seedDemoBookingsForUser` 的两张 COMPLETED 顺带开单并签署(测试档案必须能自证:已完成=有单=有积分有累计消费),或明确标注为"未开单的历史单"并让 UI 如实显示。
3. **同源断言常驻**:一笔消费一旦"已结清",订单卡/累计消费/成长值/积分/到店次数**五个读方同时算数**;反例断言:无签署单的完成单在五处一致地"不算数",且订单卡不出现「已结清」。

## 一句话给店主

积分没坏、累计消费也没坏——**是订单卡在没有结算单的时候,把预约的标价当成"已结清"显示了**;那两单是演示种子造的"有预约没开单",所以系统各处都认为没消费。修法两条:让订单卡不许再拿标价冒充已结清 + 把演示档案补成"有单有签署",两条都做完这五个数字就永远说同一句话。
