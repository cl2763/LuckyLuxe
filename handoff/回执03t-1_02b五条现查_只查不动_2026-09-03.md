## ① 多项目预约 → 多单串联结算

**现测证据**(沙箱库 `apps/api/sandbox-data/lucky-luxe.sqlite`):

结构:`settlement_groups`(带 `booking_id` + `card_owner_user_id`)→ `settlements` → `settlement_items`(带 `item_no`)
→ `settlement_technicians`(带 **`item_nos_json`** + `role` + `share_cents`)。

现景:**一组多单 9 组 · 一单多项 95 单 · 一单多技师 62 单**;
`settlement_technicians` 有 `item_nos_json` 的行 **284 / 386**。

真数据实例(项号级分账**真的在用**):
```
单 stl_mskgamyz_mtzmq → tech_mskgamwb_ role=main   项号=[1] 分成=13860
单 stl_mskgamyz_mtzmq → tech_mskgamxe_ role=assist 项号=[2] 分成=5940
单 stl_mskgb08x_390zf → tech-ava       role=main   项号=[1] 分成=6860
单 stl_mskgb08x_390zf → tech-coco      role=assist 项号=[1] 分成=2940
```
—— 既支持「项 1 归 A、项 2 归 B」,也支持「同一项 main+assist 两人分」。

**三问逐条**:

| 问 | 答 | 证据 |
|---|---|---|
| 不同项目能否分给不同技师 | **能** | `settlement_technicians.item_nos_json`,284/386 行在用,上表实例 |
| 业绩是否各归各 | **能**,按项号各有 `share_cents` | 同上 |
| 卡耗是否各归各 | **不能** | `settlements.timecard_id` 是**单级**;`settlement_items` **没有任何卡耗列**;而带卡的 12 张单**全部是多项单** |
| 小记是否各归各 | **按技师各归各,但不认项号** | `service_notes` 键是 `booking_id + technician_id + service_name`,**没有 `item_no`** |
| 签名一次还是逐项 | **逐单**(不是逐项,也不是一次) | `POST /settlements/:code/sign` 按**单号**;`signSettlement` 的 `UPDATE … WHERE id = ?` 只动那一张,**同组其余单零连带** |

**覆盖几成**:结构与分账 **≈9 成**;缺口在**卡耗与小记的粒度**、以及**多单组的签署体验**。

**缺口清单**:
1. **卡耗只有单级**:一单两项两技师、次卡只该抵其中一项时,系统说不清是哪一项耗的卡 ——
   带卡的 12 张单**全是多项单**,这不是理论风险。
2. **小记不认项号**:靠 `service_name` 字符串对应项目,同名两项无法区分。
3. **多单组逐单签**:一组 2 单顾客要签 2 次;沙箱里 **9 个多单组全部 `已签=0`**,
   这条路**没有任何已签实例**,签署体验从数据上无法观察 —— 若要「一次签全组」是新功能,不是修。
