## 零、审计方法(可复跑)

1. **表结构**:起一个全新库,`PRAGMA table_info` 遍历所有表,分出「有 tenant_id」42 张 / 「没有」14 张。
2. **SQL 租户过滤**:脚本抽取 `local-server.mjs` 里全部 `db.prepare(...)` / `db.exec(...)` 的 SQL 字符串,
   凡是命中受租户约束的表、且语句里没有 `tenant_id` 的,全部列出(命中 217 条),
   再按「只按主键 id 取单行(靠调用方校验)」166 条 / 「列表·聚合·多行」51 条分组,逐条读上下文判定。
3. **硬编码字面量**:grep `lucky-luxe` / `luckyluxe` / `Lucky Luxe` / `CAD` / `Ontario` / `America/Toronto` /

## 一、A 级 —— 已修(commit `448611c`)

### A-1 客服会话写入不带租户,被默认值收编成旗舰店的

`wechat_conversations` 两处 `INSERT` 都没写 `tenant_id`。该列是后加的,带 `DEFAULT 'lucky-luxe'` ——
于是**所有商家的客服进线都被记成旗舰店的会话**。`getWecomConversations()` 是按租户过滤的,
结果是:真商家在自己后台看不到自己的进线,而这些进线全堆在旗舰店的客服工作台里。

- 失败场景:小婕店顾客在微信问「明天有空位吗」→ 小婕在自己后台看不到 → 店主在旗舰店后台看到一条不认识的会话。
- 修法:两处 INSERT 补 `tenant_id = currentTenantId()`。
- 断言:`test-tenant-hygiene` ok 4/5/6(自己看得到、别店看不到、旗舰店也看不到)。

### A-2 AI 工作记忆写死租户

`ai_conversation_states` 的 INSERT 里 `VALUES (?, 'lucky-luxe', ...)` —— 每一家店的会话状态(意图、报价阶段、
参考图、下一步动作)都写进旗舰店名下。修法:改用 `currentTenantId()`。

### A-3 AI 学习样本第三处写死租户

`ai_learning_examples` 有三处 INSERT,`421c387` 修了两处,`workflow_logic_gap` 这处漏了。修法同上。

### A-4 薪资页列出全平台技师姓名

`/admin/finance/compensation` 里 `SELECT id, name FROM technicians WHERE is_active = 1` 没带租户,
薪资项(`staff_compensation`)倒是按租户过滤的 —— 于是**商家能看到别家店所有在职技师的姓名**(薪资为空)。

- 修法:加 `AND tenant_id = ?`。断言:ok 7。

### A-5 排班周视图返回别家店的排班行

`/admin/schedule-week` 里 `SELECT ... FROM technician_schedules WHERE date IN (...)` 只按日期取,
**全平台所有技师那几天的上下班时间都进了接口响应**(前端按本店技师列表过滤,所以界面看不出来,但数据出了租户边界)。

- 修法:再按本店技师 id 过滤。断言:ok 8。

### A-6 旧版财务汇总跨全部租户聚合

`getFinanceSummary()` 的 `FROM bookings` 完全没有租户条件,算的是**全平台**营业额与完成单数。
该接口另有一道 `FINANCE_EMAILS + FINANCE_PASSWORD` 环境变量门禁(生产未配置时直接 403),
所以现网没有实际泄漏,但门禁一旦配上就会漏。

- 修法:加 `WHERE tenant_id = ?`。断言:ok 9(凭证不符时 403 且不返回任何数字)。

### A-7 「随便挑一个」的兜底会挑到旗舰店

```js
firstActiveStoreId()  // SELECT id FROM stores WHERE is_active = 1 ... || 'store-ontario-01'
firstActiveService()  // SELECT * FROM services WHERE is_active = 1 ...
```
两个都不带租户,兜底值还写死了旗舰店的门店 id。报价转草稿链路用它们挑门店/项目 ——
**非旗舰店会把订单挂到旗舰店的门店上**。

- 修法:一律限定当前租户;挑不到返回 `null` 让上层报错,不许跨店借用。

### A-8 新客欢迎语写死品牌

`newCustomerWelcome()` 写死「您好欢迎来到 Lucky Luxe」。任何商家的新顾客第一句话都被欢迎到旗舰店。

- 修法:按 `tenantKbFacts.brandName` → 门店名 → 兜底渲染。断言:ok 15。

### A-9 支付记录币种写死 CAD

`payments` 表 INSERT 的 `currency` 写死 `'CAD'`。修法:用 `tenantCurrencyCode()`。

### A-10 会员推荐链接写死域名

### A-11 知识上下文的 tenantId 恒为种子里的 `luckyluxe`

## 二、B 级 —— 需要设计,本次只报告不动代码

### B-1 【最高优先级】全局单时区:`process.env.TZ` 钉死一个时区 —— **已在 P0.9 完成(commit `81780d5`)**

```js
process.env.TZ = process.env.APP_TIMEZONE || 'America/Toronto'
function localParts(dateLike) { ... timeZone: 'America/Toronto' ... }
```

服务端所有「今天/本月/日期分桶」都按**这一个**时区算。小婕店在中国:

- 失败场景:北京时间 8 月 8 日 08:00 = 多伦多 8 月 7 日 20:00。小婕早上打开后台看「今日预约」,
  看到的是**多伦多的昨天**;当天营业到 21:00(北京)之后的单子会被算进「明天」;
  日报、月度财务分桶、营业时间判断、排班日视图全部跟着错位一天。
- 影响面:所有非 America/Toronto 时区的商家。**小婕店已经是这种情况**(门店 timezone 已改成 Asia/Shanghai,
  但服务端日期口径没跟上)。
- 建议方案:`localParts()` / `localDateTime()` / `storeToday()` 一族改为接收 `tenantId`(或 storeId),
  从 `stores.timezone` 取时区;`process.env.TZ` 只作为兜底默认。这是一次贯穿全站的改造(排班、财务、
  报表、提醒任务、营业时间都要跟),必须单独立项 + 单独回归,不适合塞进本次清账。
- 临时缓解:老板端已改为按门店时区显示(A-12),所以**界面上的「今天」是对的**;错位只发生在服务端算的分桶上。

### B-2 小程序 59 处写死 CAD + 品牌兜底

`miniprogram` 里 `.wxml` 模板直接写 `CAD ${{...}}`,共 59 处;另有:

- `utils/api.js:180` 门店名兜底 `'Lucky Luxe Ontario'`
- `utils/i18n.js` 「定金固定为 CAD $50,不支持抵扣」
- `app.js` / `mock-data.js` 里的 `appName: 'Lucky Luxe'`

小婕店顾客在小程序里看到的全是加币。建议:后端已经按租户下发 `priceLabelZh`(A-12 之后是对的),
小程序改为**统一用后端下发的带币种文案**,不要自己拼 `CAD $`;需要一次小程序改版 + 发版。
(注:`miniprogram/utils/api.js` 当前有他人未提交的改动,本次没碰任何 miniprogram 文件。)

### B-3 老板端 i18n 词典里的静态 CAD 标签

`admin.js` 的 `copy` 词典里有「价格 CAD」「定金 CAD」「报价 CAD」「月目标 (CAD)」「底薪 (CAD/月)」等静态串。
**金额本身**已经按租户币种渲染了(A-12 的 `money()`),但这些**标签文字**还是写死 CAD。
建议:把词典里带币种的键改成函数式(接受 currency 参数),或统一去掉标签里的币种、只保留金额上的币种。
属于文案层改造,风险低但改动点分散,单独一批做更稳。

### B-4 顾客身份是全局唯一,不按租户隔离

```
SELECT users.* FROM user_identities JOIN users ... WHERE provider = ? AND provider_user_id = ?
SELECT * FROM users WHERE email = ?
```

一个微信 openid / 邮箱在全平台只对应一个 `users` 行,而 `users` 有 `tenant_id`(单一归属)。

- 失败场景:同一个顾客同时是小婕店和旗舰店的客人 → 他只能属于其中一家;
  后进的那家要么复用别家的档案(串味),要么建不出来。
- 建议方案:身份(identity)保持全局,**顾客档案(users)改为 identity × tenant 的一对多**;
  或增加 `tenant_members` 关联表。涉及存量数据迁移,必须单独设计。

### B-5 七张子表没有 tenant_id —— **已在 P0.9 完成(commit `81780d5`)**

`payments` / `technician_schedules` / `business_hours` / `store_special_dates` / `booking_slots` / `booking_status_history` / `booking_drafts`

现状**安全**:所有查询都以租户受限的父键(`booking_id` / `technician_id` / `store_id`)为条件,
租户身份可从父表推导(A-5 那处例外,已修)。

- 风险场景:今后任何**直查这些表做报表/清理**的新代码,只要不 join 父表,就会跨店。
- 建议:要么补 `tenant_id`(用父表回填),要么在这些表上建视图并约定「不许直查裸表」。
  倾向补列 —— 一次性成本低,以后不用靠人记纪律。

### B-6 `LL-` 会员码 / 券码前缀写死

`LL-XXXXXXXX`(会员码)、`LL-XXXX-XXXX`(券码/兑换码)是旗舰店品牌缩写,所有商家共用。

- 现状不会撞号(随机段足够),纯品牌问题:小婕店顾客拿到的券码也是 `LL-` 开头。
- 建议:租户级可配前缀,默认 `LL-`。**注意存量会员码已发给顾客,改前缀要考虑老码继续可用。**

## 三、C 级 —— 确认无害(附原因)

| 项 | 为什么无害 |
|---|---|
| `KB_SEED_TENANT_IDS = {lucky-luxe, luckyluxe}` | 白名单**就是**用来只让旗舰店吃静态种子的 tenant 层,是隔离机制本身,不是漏洞 |
| 建表语句里的 `tenant_id ... DEFAULT 'lucky-luxe'` | 是给存量行回填用的默认值。**前提是所有 INSERT 都显式写 tenant_id** —— A-1/A-2/A-3 正是违反了这个前提;其余 INSERT 已核对全部显式写入 |
| `DEFAULT_TENANT_ID` 的各处使用 | 都在「无租户上下文时的兜底」位置(公开接口未带 x-tenant-id、平台脚本),`validTenantId()` 会校验后回落,行为明确 |
| 演示种子里的 `demo-cust-01` / `Lucky Luxe Owner` / demo 登录旁路 | 全部在 `ALLOW_DEMO_ADMIN_LOGIN=true` 或 `currentTenantId() === DEFAULT_TENANT_ID` 门禁内,生产不走 |
| `expireOldHolds()` 扫全表过期占位 | 定时清理任务,本来就该跨租户跑 |
| `/platform/*` 的跨租户聚合(概览、计费、租户列表) | 平台运营视角,按设计就是全平台 |
| `admin_accounts WHERE LOWER(username) = ?` | 用户名全平台唯一(建号时就做了唯一性检查),按名字查不会串店 |
| `technician_services` / `booking_slots` 等联结表 | 两端 id 都受租户约束,不存在跨店组合 |
| `plans` / `platform_kb_entries` / `merchant_leads` / `tenants` | 本来就是平台级全局表 |
| `payments` 按 `booking_id` 查、`business_hours` 按 `store_id` 查等 | 父键已受租户约束(详见 B-5) |
| `formatCadFromCents` 等金额函数 | `8c7edc7` 已改为按租户币种;兜底 `'CAD'` 只在完全取不到门店币种时命中 |

## 五、结论:这类病还会不会再犯

三次串味的**共同根因**是同一句话:**「代码里出现一个具体值,而它其实是某一家店的事实。」**
本次把这句话对应的所有形态都扫了一遍:写死的字符串(A-7~A-12)、写死的 SQL 常量(A-2/A-3)、
漏掉的 WHERE(A-1/A-4/A-5/A-6)、以及默认值悄悄替你选了租户(A-1 最阴险 —— 代码里根本看不见 `'lucky-luxe'`,
它藏在建表语句的 `DEFAULT` 里)。

**留下的防线**:`test-tenant-hygiene.mjs` 15 条断言 + `verify-jics-kb.mjs` 的泄漏词表。
新增租户级功能时,建议顺手往这两个文件里加一条断言,比事后审计便宜得多。

**新增纪律(P0.9 起生效)**:
1. **今后直查那七张子表,必须带 `tenant_id` 过滤** —— 列已经补齐、触发器保证新写入带租户,
   所以不再有「只能靠 join 父表」的借口。裸查 `payments` / `booking_slots` / `business_hours` 等
   而不带 `tenant_id` 的新代码,视为 bug。
2. **业务上的「今天/本月」一律走 `todayOf(tenantId)` / `monthKeyOf(tenantId)`**,
   不要再写 `localParts(new Date()).date` 之外的自制日期逻辑,更不要直接用 `new Date()` 推日期。
3. 加 `tenant_id` 列时**不要带 `DEFAULT '<某个租户>'`**。A-1 的教训:默认值会让漏写的 INSERT
   悄悄归到旗舰店名下,而代码里根本看不见那个租户 id。宁可留 NULL 让回归炸出来。

**还没清的**:B-4(顾客身份归属)是真正的架构级假设,不是随手能改的。
B-2(小程序 59 处 CAD)归境内小程序发版批次;B-3 / B-6 挂账。
