## §零 现状(我读码)
- **主服务的链路是全的**:回调验签、`kf/sync_msg` 拉消息、`kf/send_msg` 回消息、按 `open_kfid` 路由到店(`wecom-routing.mjs`)、AI 接待走 `handleWecomInbound`。
- **卡在出口 IP**:`local-server.mjs:1515` 写死直连 `qyapi.weixin.qq.com`,从 Railway 出去,出口 IP 不固定 → 企微「可信 IP」填不了 → gettoken 会被拒。
- **`apps/wecom-gateway/` 早就写好了一个固定 IP 网关**(收回调转主服务、代发企微 API),但它规划在 DigitalOcean `165.227.255.152` + `wecom.luckyluxeatelier.com`(境外、非备案域)—— 与现在的境内路线不一致,**从没部署**。
- **现在有更好的落点**:腾讯云北京那台(`api.jingshengyouji.com`,备案域、固定公网 IP、证书在、11g/11h 已验通)。
- 空的:五个环境变量(`WECOM_CORP_ID / CUSTOMER_SERVICE_SECRET / TOKEN / AES_KEY / OPEN_KFID`)、企微后台的可信域名/可信 IP/回调 URL、每店 `open_kfid`。

## §一 Code 做(不碰 Railway 配置、不看密钥,J-110:那台机跑着官网,只加不改)
1. **网关改部署到腾讯云那台**:`apps/wecom-gateway` 的 `UPSTREAM_BASE_URL` 改指 Railway 主服务;新增一份 nginx 站点片段(`location /wecom/` → 网关端口),**不改官网那份配置**;网关用 systemd 常驻。部署步骤写成店主可照抄的清单(她有那台机的登录,Code 没有;11f 那套做法)。
2. **主服务出站改走网关**:`WECOM_API_BASE` 从写死改为读环境变量,默认仍直连(不破坏现状);设成 `https://api.jingshengyouji.com/wecom/cgi-bin` 时全部企微 API 调用经网关固定 IP 出去。网关只转发 `/cgi-bin/gettoken|kf/*` 白名单路径,其余 403;**access_token 不落日志**。
3. **回调入口**:企微回调 URL 定为 `https://api.jingshengyouji.com/wecom/callback`,网关验签后转主服务 `/wechat/customer-service/webhook`。
4. **自检页** `GET /wecom/health`(网关):返回「出口 IP、能否取到 token(是/否,不回 token)、上游可达」三项,店主配完一眼看得出哪步没通。
5. 判据:沙箱起网关 + 主服务,用 stub 企微服务端验:①回调 GET 验签通过 ②POST 事件 → 主服务收到 → sync_msg 拉到一条 → AI 回复经网关 send_msg 发出 ③白名单外路径 403 ④网关日志 grep 不到 token。落刀:拆掉白名单 → 红。
