## 二 · 裁#90 的「或」原本是什么(`data-scope.mjs:79-84`)

```js
export function demoLoginAllowed({ dataDir = '', env = process.env } = {}) {
  if (isProductionEnv(env)) return false                        // ① 环境变量说是生产 → 关
  if (!DEMO_OK_SCOPES.has(scopeOf(dataDir, env))) return false   // ② 库域不是 ci/sandbox → 关
  return env.ALLOW_DEMO_ADMIN_LOGIN === 'true'
}
```

裁#90 的原话口径:**「不许把 `IS_PRODUCTION` 换成库域判断」**(换掉可能在某个组合下把门打开),
**正确形状是两个判据任一说「这是真的」就关** —— **只会更严,永远不会更松**。

## 三 · 提议的改法(**一行**)

```js
// local-server.mjs:168 附近,新增一个"当真环境办"的合并判据,原 IS_PRODUCTION 一个字不动
const TREAT_AS_REAL = IS_PRODUCTION || !DEV_SCOPES.has(DATA_SCOPE_NAME)   // DEV_SCOPES = {ci, sandbox}
// 两处调用把 isProduction: IS_PRODUCTION 换成 isProduction: TREAT_AS_REAL
```

**为什么第二个判据写成 `!DEV_SCOPES.has(...)` 而不是 `=== 'production'`**:
🔴 **生产库路径以 `local-data` 收尾,`scopeOf` 在生产上返回的是 `'local'`,不是 `'production'`**(09p §一 现查)。
拿 `=== 'production'` 判,**在生产上永远不成立,等于没加**。
白名单式(「不是开发档就按真环境办」)才是**朝严那一侧**的写法。

## 四 · 🔴 三向都报(不许只报一向)

**现测各库域的判定**(直接跑 `scopeOf` 得出):

| 库 | `scopeOf` | 在 `DEV_SCOPES` 里? | 改后 `TREAT_AS_REAL` |
|---|---|---|---|
| **生产库**(容器 `/app/apps/api/local-data`)| `local` | 否 | **true → 跳过** |
| **本机库**(`apps/api/local-data`)| `local` | 否 | **true → 跳过** 🔴 |
| **沙箱库**(`apps/api/sandbox-data`)| `sandbox` | 是 | false → 照跑 |
| **回归临时库**(`/tmp/ll-ci-data.*`)| `ci` | 是 | false → 照跑 |

### 向① · `IS_PRODUCTION` **已设** → 会跑吗

**改前:跳过。改后:跳过。** 第一个判据先成立,**行为一个字不变。**

### 向② · `IS_PRODUCTION` **没设** → 会跑吗

- **改前:会跑** —— 这正是那个缺口:生产上万一这个变量没设,两条迁移会去改 `tenants.kind` 与 `users.tags_json`。
- **改后:不跑** —— `scopeOf('/app/apps/api/local-data') = 'local'`,不在 `DEV_SCOPES` 里 ⇒ 按真环境办 ⇒ 跳过。**缺口堵上。**
- 🔴 **代价要说清**:**本机库也会一起被判成"真环境",那两条迁移在店主本机也不再跑。**
  - 现测本机库里两条标记**都已经在了**(`demo_retire_backfill_v1` / `tenant_kind_backfill_v1`),**跑过了,不跑也没影响**;
  - **但以后本机库若被重置/重建,这两条迁移就不会自动跑了** —— 要跑得手动或另开口。
  - **这是这个改法唯一的真代价,请你裁**:是接受它,还是把本机库单独放行(那就又多一个例外,而例外正是三个病的根)。

### 向③ · **设错**会怎样

| 设错的样子 | 改前 | 改后 |
|---|---|---|
| 生产上 `RAILWAY_ENVIRONMENT` 丢了 | 🔴 **跑**(缺口) | **跳过**(库域兜住) |
| 店主本机 shell 里常设着 `NODE_ENV=production`(**现实就是这样**)| 跳过 | 跳过 |
| 库域判不出(`unknown`,例如换了挂载点) | 看变量 | **跳过**(`unknown ∉ DEV_SCOPES`) |
| 沙箱被误设 `NODE_ENV=production` | 跳过 | 跳过 |

🔴 **四种设错,改后一律朝「跳过」那边倒** —— **没有任何一种组合会让它在真环境上跑起来。**
合 J-68:**尺子的误差方向锁死在对自己不利那一侧。**

## 五 · 判据怎么守(改了之后要配的刀,一并报批)

1. **两向行为刀**:同一份基准库开两次机 ——
   `DATA_DIR` 在 `local-data` 形状下 → **两条迁移标记都不许出现**;
   `DATA_DIR` 在 `/tmp/ll-ci-data.*` 下 → **必须出现**。
   (本批已经有现成的夹具做法:`09q_推后加法清单_两栏` 那两次开机就是这么跑的。)
2. **静态刀**:全仓「决定要不要写真环境」的守卫**必须是两个判据的或**,
   单靠 `IS_PRODUCTION` 的位置**逐个落进白名单并写理由**,上限只许变短。
3. 🔴 **反例数据**:基准库里**必须先把两条标记摘掉**,否则两边都"没新增",刀空转 ——
   **我这次第一遍就是这么空转的**(L4)。
