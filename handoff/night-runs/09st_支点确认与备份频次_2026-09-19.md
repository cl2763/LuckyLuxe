# 一 🔴🔴 最要紧的一件:**`IS_PRODUCTION` 在生产上是 true,A 栏从来就不成立**

## 事实(生产容器内只读现测)

```
DATA_DIR            : 没设 → 回落到 <容器>/apps/api/local-data
BACKUP_ENABLED      : 已设,值="true"
NODE_ENV            : 已设,值="production"      ← 🔴
RAILWAY_ENVIRONMENT : 已设,值="production"      ← 🔴
```

## 为什么会问岔

**`IS_PRODUCTION` 不是一个环境变量,它是我们代码里的一个常量**:

```
apps/api/local-server.mjs:168   const IS_PRODUCTION = isProductionEnv()
apps/api/data-scope.mjs:75      isProductionEnv = NODE_ENV === 'production' || Boolean(RAILWAY_ENVIRONMENT)
```

**店主答「没设」是对的 —— Railway 上确实没有叫 `IS_PRODUCTION` 的变量。**
**而它依赖的那两个变量,两个都设着。**

## 结论

> 🔴 **`IS_PRODUCTION` 在生产上求值为 `true` ⇒ 走 **B 栏**,不是 A 栏。**
> **那两条迁移在推上去之后不会跑 —— 而且就算没有我 09r 那个「或」,它们也不会跑。**
> **09s「A 栏成立 ⇒ 不推」那条前提,不成立。**

🟡 **但 09r 那个「或」不白做**:它把「万一哪天这两个变量掉了」那一向也堵上了(纵深),
而且它现在挡的东西比那两条迁移多。**只是它不再是这次推的承重点。**

# 二 🟢 09t §一 那一句确认:**就地关闭**

**问**:九向里那个「生产库」,是真生产的算法,还是本机替身?
**答**:**真生产的路径,而且那个路径是量出来的,不是写下来的。**

1. **`DATA_SCOPE_NAME` 与 `scopeOf()` 是同一件事**
   `apps/api/local-server.mjs:130` → `const DATA_SCOPE_NAME = scopeOf(dataDir)`
2. **生产上的 `dataDir` 是多少**
   `local-server.mjs:128` → `process.env.DATA_DIR ? resolve(…) : join(__dirname, 'local-data')`
   生产 `DATA_DIR` **没设**(上面现测)⇒ 回落 = `/app/apps/api/local-data`
   🔴 **而这正是 `railway ssh` 读 `/proc/1/fd` 量到的那个路径**(`fd 17 -> /app/apps/api/local-data/lucky-luxe.sqlite`)。
   **两条独立证据对上了:一条从代码推、一条从进程量。**
3. **`DEV_SCOPES` 成员逐个列出**
   `apps/api/secret-gate.mjs:17` → `new Set(['ci', 'sandbox'])` —— **共 2 个,没有 `'local'`**
4. **当场判**
   ```
   scopeOf('/app/apps/api/local-data')  = "local"
   DEV_SCOPES.has("local")              = false
   !DEV_SCOPES.has("local")             = true    ← 那个「或」的第二个判据,在生产上为真
   ```

## 🔴 把 09s §一 那个担心说清楚

09s 担心的是:**「如果 `'local'` 又在 `DEV_SCOPES` 里 —— 那这个「或」在生产上等于没加。」**
**它不在。** 混淆点在于两个集合不是一回事:

| | 是什么 | 成员 |
|---|---|---|
| `scopeOf()` 的返回值域 | **库域的名字**,四个 | `ci` / `sandbox` / `local` / `production`(+ `unknown`) |
| `DEV_SCOPES` | **哪几个库域算开发档** | **只有 `ci` 与 `sandbox`** |

**`'local'` 是一个库域名字,但它不是一个开发档。** 所以 `!DEV_SCOPES.has('local')` 为真,「或」成立。

# 三 🟢 09t §二:备份频次两个数**对得上**,而且定出了推后该验哪一次

## 事实

```
BACKUP_ENABLED = "true"                       ← 定时器确实在跑
进程起于         Tue Aug 25 16:55:08 UTC 2026  ← 已连续运行 23 天 23 小时,中间没重启过
日备时间戳       每天 04:55:11 UTC(毫秒位 065 / 097 / 256 / 194,正常 setInterval 抖动)
容器时区         UTC(TZ 空);门店时区 America/Toronto(应用内钉死)
```

## 对账(三种可能里是第 2 种,但要说准)

`setInterval(runBackup, 6h)`,锚点 = 进程启动 **16:55 UTC** ⇒ 节拍 **16:55 · 22:55 · 04:55 · 10:55**。
`dailyBackup()`(`db-backup.mjs:99`)那一行:

```js
const made = existsSync(dest) ? null : snapshotDb({ … })   // ← 当天文件已存在就跳过
const dest = join(backupDir, `lucky-luxe-${dateStr}.sqlite`)  // dateStr 按**门店时区**算
```

多伦多午夜 = **04:00 UTC**(EDT, UTC−4)⇒ **04:55 那一拍是跨过门店午夜后的第一拍**,
`dateStr` 变成新的一天 ⇒ 建文件;其余三拍看到当天文件已在 ⇒ 跳过。

> 🔴 **所以不是「每天 4 份只留 1 份」,是「一天只建 1 次,另外 3 拍空转」。**
> **两个数严丝合缝对上了。`db-backup.mjs` 就是生产日备的出口,09o 那句「唯一出口」站得住。**

## 🔴 推后该验哪一次 —— 这一格会变,不说清就会等错时间

**推 = 容器重启 = 定时器锚点从「16:55」换成「推的那一刻」。**

- **重启当下就会立刻跑一次** `runBackup()`:若当天(门店时区)的文件还没有 → **当场建一份**;已有 → 跳过。
- **此后的节拍** = 推的时刻 + 6h × n。**跨过多伦多午夜(04:00 UTC)后的第一拍**才是新一天那一份。

**⇒ 推后核验的正确做法(已登记进推后待办)**:
1. **推完当下**先看一眼 `backups/` 有没有多一份(那是重启那一跑);
2. **真正要验的是「第一次在 WAL 下、按新节拍建出来的那份日备」** ——
   **时间 = 推的时刻(UTC)向后找第一个跨过 04:00 UTC 的 6 小时节拍**,不是固定的 04:55。
3. 打开它逐表点行数,与生产库对(做法与 09q 那次一样)。
