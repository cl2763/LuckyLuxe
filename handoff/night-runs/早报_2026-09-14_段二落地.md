## 你看得见的、变好的三件

### 一、「解密」这一步以前在回归里根本走不到 —— 你昨天点破的那个坑,是真坑

你说的原话是:手机号解密要的 `session_key` 正是 `jscode2session` 给的,**而替身给的是假的**。
查下去比这更糟一点:替身给的是一句字面量 `'stub-session'`,
**用它谁也解不出任何东西** —— 也就是说,不管后端那段解密写成什么样(甚至压根不写),
套件都会绿。这就是你说的「站在门后面的绿」。

按你的令做了:替身**给出一把确定的 key**(由 openid 推出来,同一个人两次登录同一把),
夹具**用那把 key 按真算法加密**一份载荷,服务端**照真算法解密**。
被替的仍然只有「问腾讯这个 code 是谁」那一跳,**加解密两头都是真的**。

然后按你的规矩造病,五刀:密文改一字节 / iv 改一字节 / 换别人的 key /
拿别人的 code 来绑 / 未登录。**五刀全红,各自点名。**
最要紧的是行为层那一刀,它红出来的样子是:

```
status=200  库里phone=""  tags=[]
```

一个坏掉的密文,换来一个 **200**、一个**空号**,连「无手机号」标记都被摘掉了 ——
这个人从此在后台永远认不出来,而界面上一切正常。
现在它必须 400,库里那一格必须仍然是空的。

顺带**归因**你要的那一步:同一份病喂旧判据 `test-wechat-stub`,**旧的是绿的**(10 项全过)。
说明这层盖的是从没被看过的地面,不是把旧判据翻个面。

### 二、顾客跳过头像昵称时,我们本来会把她的数据库主键当名字显示给她

查「跳过不许拦路」那一条的时候撞见的。跳过之后名字的兜底是这么写的:

```js
member.nickname || member.id || member.memberCode || '微信用户'
```

没昵称 → 落 `member.id`。顾客在自己的「我的」页上看到的是一串 `user_xxxxxxx`。
「微信用户」那个词写在最后,**永远轮不到**。

这就是《假数回落红线》第 1 条禁的那种写法:`a || b || c`,三个东西三个语义,
拿主键顶昵称。改成直接落「微信用户」,判据 ㋐14 常驻。
(造病的时候有个细节值得说:我把它改回 `member.id` 试刀,判据红了,
**而那一行的注释还写着正确的规矩** —— 判据读的是代码,不是注释。)

### 三、我们越把夹具改成走正门,门关档就越少扫一套 —— 而判据全程绿

这个是查「门关档该跑是 12 还是 13」时挖出来的,比那个数字本身要紧。

门关档「该跑哪些」是按机制算的:源码里出现**顾客侧取/用 token 的形态**就算。
但那串形态只认**演示登录、邮箱登录**那几种写法 —— **不认微信正门**。

后果反过来了:裁 #60 让我们一套套把夹具改成走正门,
**每改成一套,那一套就从「该跑」名单里掉出去一个**,覆盖数一路变小,而判据一路绿。
新写的 `mini-phone` 就落在这个盲区里 —— 它是纯正门的,机制认不出它。

补上正门形态之后:**该跑 12 → 13**(新认出来的正是 mini-phone),**该跑没跑仍是 0**。
配了一条造病守着:构造一段只有正门形态的夹具,机制必须认得出。
