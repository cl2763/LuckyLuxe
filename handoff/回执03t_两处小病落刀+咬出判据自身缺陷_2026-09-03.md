## 二、🔴 顺带查实一个**判据自身的缺陷**(J 族),它已经骗了我三轮

### 现象

`mp-overlap` / `mp-home-sections` 连着三轮回归被判 **0 断言**,报
「沙箱进程起于源码之前 N 秒」;而我**单跑同一把刀是 4/4 全绿**。
更可疑的是 N 两轮都是同一个数(1874),而两轮相隔九分钟。

### 我先做的事:让判据指认现场

它原来只报「差 N 秒」,说不出是**哪个进程、哪个文件**,人就只能猜产品有问题。
先给它加了现场行(pid + 起始时刻 + 最新源码文件与改动时刻)。这一行立刻把真相打了出来:

```
现场:4310 pid=59534 起于 2026-09-02T12:05:31Z · 最新源码 quote-state.mjs 改于 13:15:28Z
```

pid 59534 根本不是沙箱。

### 病根

```js
lsof -ti :4310        // ← 原来这么写
```

**`lsof -i :端口` 会把客户端连接也算进去。** 现测:

```
pid=59534  wechatweb  TCP localhost:65234->localhost:4310 (CLOSED)   ← 排在第一
pid=77685  node       TCP *:4310 (LISTEN)                             ← 真正的沙箱
```

代码取 `[0]`,于是它一直拿**微信开发者工具的启动时刻**当"沙箱启动时刻"去跟源码比。
工具是 20:05 开的、沙箱是 21:16 起的 —— 所以永远"起于源码之前"。

**两面都有后果**:
- **误红** —— 两把刀连着三轮被判 0 断言,而产品完全正常;
- **误绿** —— 哪天某个客户端进程比源码新,它就放行一个**真正过期**的沙箱。

**判据不确定比判据错更糟**:同一份代码单跑绿、整轮红,人只会去怀疑产品。

### 改法与归因

只认监听者:`lsof -ti :4310 -sTCP:LISTEN`;多于一个监听者时在现场行里写明。

**归因(同一份现场,两把判据各取到谁)**:

| | 取到 pid | 是谁 | 启动时刻 |
|---|---|---|---|
| 旧判据 | 59534 | `wechatwebdevtools` | 20:05:31 |
| 新判据 | 77685 | `node local-server.mjs` | **21:16:35** |

改完之后它**立刻又红了一次,而这次是对的** —— 我刚改完 `test-need-sandbox.mjs`,
源码确实比沙箱新。重起沙箱后单跑 4/4 绿、整轮 80/80 绿。

**这也说明我此前三轮的「重起沙箱」其实都是好的** —— 一直是判据在读错东西。
