## 🔴 造病(店主 07l §一 点名要的那一条)—— 结果比「红了」更值得看

**做法**:挑 `/my/stored-value/confirm`(顾客可见 **且** 涉钱,清单里第一梯队),
把**落库那一行**注掉,接口照样回 200,界面照常弹「已确认到账」。

```diff
- db.prepare('UPDATE stored_value_transactions SET customer_confirmed_at = ? WHERE id = ? AND customer_confirmed_at IS NULL').run(now, row.id)
+ /* ☠️ J-62 造病:落库这一步注掉,接口照样回 200,界面照常弹「已确认到账」 */
```

**套件红了**(`test-noshow-aftersales` 退出码 1)。**但红的不是该红的那一条。**

```
ok 279 - ㋁ 确认成功(200+confirmedAt)          ← 病在身上,它**还是绿的**
❌      - ㋁ 幂等:重复确认=200 already,时间戳不变  ← 红的是这条,而且是**撞上的**
```

那条名字叫「确认成功」的判据,原文是:

```js
check('㋁ 确认成功(200+confirmedAt)',
  cf1.status === 200 && cf1.data.confirmed === true && Boolean(cf1.data.confirmedAt), …)
```

**三个条件全部取自接口的返回体,一个字都没查库。** 返回体是处理函数自己拼出来的 ——
落不落库它都长一样。所以这条判据验的是**「接口说成了」**,不是**「真的成了」**。

真正咬住这一刀的是隔壁那条幂等:因为没落库,第二次确认又成功了一遍,时间戳变了,它才红。
**换句话说:这一处能被发现,是运气,不是判据。**
如果当初没写那条幂等,这一刀会**全绿通过**。

> 这就是 J-62 要治的东西,而且它证明了店主那句话的第二层:
> **不只是产品会「界面说成了而没成」,判据也会「验了界面就当验过了」。**

**结论(§一 的造病要求已满足,且给出的信息比要求的多)**:
- 造得出红 ✅
- 但**该守的那条没守住** —— 记为缺陷,治法见下方「要你定」第 1 条。

- 同一处的 `display_name` 是**真存了**的 —— 所以这不是「这个功能没做」,是**做了一半,回执给全了**。
