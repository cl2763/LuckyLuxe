# 有迹 · 交付自检闭环（Code 作业纪律 · 2026-08-10 店主定）

> 立规背景：08-10 开检一次抓出 32 条，其中大量是**此前已被 Code 报告为"完成/核验通过"的部分**。
> 问题不在能力，在**验证层级错位**——在写代码那一层验（接口/断言），店主在看得见那一层用（渲染出来的页面）。
> 本文把五种失败模式各钉一条硬机制，**入 CLAUDE.md 永久生效**。

---

## 一、五种失败模式与对应机制

| # | 失败模式 | 真实案例 | 机制 |
|---|---|---|---|
| L1 | **在错误的层级验证** | D2/D3「代码+接口层验收通过」，但顾客端一个徽标都没渲染（中间隔着白名单映射层） | **末端验证律**：凡交付物是界面，最后一步必须是"在店主会看到的那一层"截图对照。断言绿是必要条件，不是充分条件 |
| L2 | **修实例不扫同类** | 「今天」按钮修了，排班「本周」同一个毛病没动；商家端币种修了，顾客端 51 处没动 | **同类扫尽律**：每修一个缺陷，必须回答"它属于哪一类？全仓还有几处同类？"并给出机械搜索证据（0 残留） |
| L3 | **无验收标准却报完成** | A1 价目表编辑器"逻辑混乱"——这屏从来没有 UI 图，也就从来没有对照物 | **无图不结案律**：没有 UI 图、也没有书面"对的样子"的界面，**不许标记为已验证**。必须挂 ⬜ 并上报 Cowork 补标准 |
| L4 | **用不会暴露 bug 的数据验** | 日结分成用单技师单验过；更正卡用无更正的单验过；「今天」用当天验过 | **反例数据律**：验证前先问"什么数据能让它露馅？"，然后**用那个数据验**。至少覆盖：多对象、非当期、异常态、空态 |
| L5 | **一次成功就宣布稳定** | 「确认签字」第一次点不动第二次可以，此前按"偶发/工具限制"结案 | **重复稳定律**：交互类（点击/输入/签字/提交）必须**连续 5 次进出页面**都成功才算通过。出现 1 次异常＝缺陷，不许写"偶发" |

## 二、复发登记（这是"闭环"的闭合处）

任何缺陷若属于**此前已宣布修复的同一类**（如币种已是第三次），必须额外产出：

1. **上一次的修复为什么没兜住**（漏了哪个目录/哪种写法/哪一层）；
2. **一条永久护栏**（断言或扫描规则），而不只是修这一处；
3. 写进《小程序开发日志》当日一节的"复发"小标题下。

> 判据：如果这个缺陷下次还能靠同样的疏忽再来一遍，说明护栏没装上，不许结案。

## 三、交付报告固定结构（结构本身就是自检表）

每条交付/修复的回报必须带满六项，**填不出来的那一项就是没做的那一步**：

```
[编号] R2 开单改项目金额不变
① 改了什么      ：settlement 表单变更后强制重取后端合计
② 在哪一层验的  ：模拟器实机操作截图（不是断言）—— 选A→加B→改档，合计三次都变
③ 同类扫尽      ：全仓搜"本地缓存金额"写法，另有 1 处（加项数量步进）同样修掉，现 0 残留
④ 用什么数据验的：多项目+加项+双技师+会员档（能让它露馅的组合）
⑤ 重复稳定性    ：连续 20 次增删改，合计每次都变（交互类需 ≥5 次）
⑥ 残留与不确定  ：无 ／ 或如实写"××尚未验证，原因××"
```

## 四、边界：什么时候必须停下来问，而不是自己判断

- 界面**没有图**、或图上没画过这个状态 → 停，报 Cowork（L3）
- 修复会**改变业务口径**（金额、归属、权限、时间口径）→ 停，先改文档再动手（文档归口纪律）
- 现象**无法复现或无法下结论** → 不许挂着；能靠店主一次操作裁定的，当场请店主裁定（既有纪律）
- 发现的问题**比手上任务更严重** → 停下来先报（08-10 顾客端币种就是这么捞出来的，做得对）

## 四之二、批次作业三防（2026-08-10 晚增补 · Code 第三次犯排序错后自提、Cowork 拍板采纳）

> 背景：连续三批出现"不可估时任务卡队首→整轮余量耗尽→零交付"。第三次复发按规矩不再检讨，改立机制：

1. **时间盒**：查根因/复现类任务（天然不可估时）给 **30 分钟盒子**。到点没结果→立即转"请店主一次操作裁定"（附上已排除项，让店主的裁定有的放矢），不再自己耗。D9 是首个适用案例。
2. **每轮先交一件**：批次开始先挑**最独立、纯代码**的一件做完并推掉，再动其余——保证任何一轮都不归零。
3. **模拟器集中做**：所有需要模拟器/自动化端口的验证（L1 截图、L5 连续 N 次）排在一轮的**同一时段连做**；端口一掉先重启工具再继续，不穿插分散。

## 四之三、防空转闸门（2026-08-10 晚增补 · 新故障类立规）

**故障类**：断言排在破坏性用例（停用账号/删除数据）之后 → token 失效/集合恒空 → `every()/all()` 类断言**空转通过**——"看起来绿其实没测"。
**规**：一切 every/all 类断言之前，必须先断言**集合非空**（如 `assert list.length > 0`）；fixture 每一步必须检查返回值（mustOk）。防空转闸门是门禁类套件的标配，不是可选项。

## 四之四、模拟器占用声明（2026-08-10 深夜增补 · D9/D15 测试污染事件后立规）

> 背景：Code 自动化连续 5 小时占用模拟器未声明，店主同期开检，撞出两个"灵异缺陷"——D15（点「我的」跳客户库）已实锤为 Code 的 L5 脚本 reLaunch 循环所致。两个假缺陷耗掉双方多轮排查。

1. **占用开关**：自动化跑批前在 `handoff/` 写 `自动化占用中.txt`（写明开始时间与预计时长），跑完立即删除；
2. **分时使用**：店主开检时段不跑自动化；见到开关文件存在，店主不动模拟器；
3. **灵异现象第一排查项**：凡"间歇性/自愈型/解释不通"的界面现象，第一个要排查的是**当时是否有自动化在跑**，排除污染后才立缺陷编号。

## 四之五、套件时间确定性（2026-08-11 凌晨增补 · 「白天绿半夜红」事件后立规）

> 背景：test-perf-base-migration 在 08-10 19:26 全绿，同一套件凌晨跑红——套件建的单落在跨日边界上，白天跑不出来。拍板①（日结归属=服务发生日）的一个真实边界缺陷被"跑套件的时间点"掩盖了数日。

1. **全量回归的绿必须与挂钟时间无关**：任何"只在某些时刻能过"的套件本身就是缺陷；
2. **时间敏感断言必须注入固定时钟**（测试内指定"现在"，不用真实 now）；
3. **边界用例显式建**：跨零点（23:59 服务 / 00:01 签署）、跨月、且**两个门店时区（America/Toronto 与 Asia/Shanghai）各建一份**——日界必须按门店时区算，不是服务器时区。

## 四之六、页内组合测试（2026-08-12 店主立规）

> 背景：D22 的幽灵项目正是"跨大类选择 × 切换大类"两个功能**组合**才触发的——每条路单测都绿，组合就漏。店主明确要求：功能页验收必须组合测。

1. **凡交付/改动一个功能页，验收必须包含页内功能的组合矩阵**：页内每个可交互功能（选择、切换、添加、移除、勾选、跳转）至少**两两组合**各测一遍；涉钱页面的关键路径做**全组合**；
2. 回报里附**组合矩阵**（哪些组合测了、结果如何、哪些组合判定不适用及原因）——"单功能各自 L5 全绿"不能替代组合矩阵；
3. 组合中发现的缺陷按 L2 惯例问同类：这个组合坏了，结构相同的其他组合呢。

## 四之七、弹层实点律（2026-08-12 D26/D27 复发登记后立规）

> 背景：收尾三件批断言链全绿，店主一点弹层就断三处——复制静默失败（隐私校验拦截无 fail 回调）、链接无处理器（死链）、财务转场层残留冻死全 App。共同漏洞：L5 用 `callMethod` 直呼处理器，把**遮罩层级、隐私校验、无处理器死链**三类问题全绕过去了。

1. **凡弹层/浮层上的交互控件，L5 必须 `element.tap()` 实点**，不许 callMethod 代替——触点到控件之间那一层（层级、遮罩、绑定）正是 callMethod 测不到的地方；
2. **涉剪贴板必须读回剪贴板断言**（复制→读回≡预期串），不以 toast 出现为准；
3. **无可见浮层时，页面全屏遮罩节点数必须为 0**（护栏断言常驻）；微信原生转场层查询不到，所以**进出页路径必须实点走通**（D27 教训：导航栈卡死只有实点能暴露）；
4. 涉及微信隐私接口（剪贴板/相册/定位等）的功能，**发版清单必须含 scope 声明检查项＋真机复验条款**——沙盒 `__usePrivacyCheck__:false` 只是沙盒放行，不是验证。

## 四之八、波及面回归律（2026-08-12 店主立规 · 源起:店主每扫必中新雷,责成全面反思后定）

> 店主原话:"扫一遍所有的漏洞——这次 P0–P2 的修改让哪些原来能用的功能不能用了、受影响了?改的东西是不是相关的地方还没完全改过来?"背景案例:D28(D10 修复批埋雷,此后连续多批全绿无人发现)、D29(D27 修门禁只修两页漏了工资)、D30(修绑定码弹层漏了签署码弹层)。详细分析见《反思与回归扫雷计划_2026-08-12.md》。

1. **改共享件必交血缘清单**:凡批次动了共享件(mixin/弹窗组件/门禁/api.js/金额出口/引擎接口/数据源/路由),回报必须带**全仓使用方清单(文件+行)+逐个使用方验证结果**——"应该没影响"四个字禁用,填不出清单=没做完;
2. **L2 的"类"必须按机制定义,不按长相**:先写类定义(哪个 API/哪个组件/哪种写法),再给机械扫描证据;**这条对 Cowork 同样生效**——指令按机制圈类,不按症状圈页面;
3. **每批收工前跑《用户路径总清单》全量实点回归**(老板端/员工端/顾客端全部主路径,element.tap 实点,常驻夜跑资产):任何一条路径断=本批不许收工——把"店主扫雷"变成"机器先扫,店主终审";
4. **wx.* 异步调用一律有 fail 处理**:全仓扫描无 fail 回调的调用点 0 残留,CI 常驻(静默失败家族的总闸:D26 复制、D28 弹窗都是同一族);
5. **修复批与功能批同责**:修复批不是"改完就走"——它动过的每一处,下一批全量回归照样要过。埋雷两天没人发现的事(D28)不许再有。

## 四之九、双端同病检查律（2026-08-12 店主立规）

> 店主原话:"我不可能两个端口同时检查,工作量太大,我一般只查一个端。我发现一个问题的时候,要看它在另外一个端口是不是也有问题:有就改正;没有的话要总结为什么两个端口不一样——是不是出现了底层逻辑的问题?"网页版与小程序版只是架构不一样,**里面每一个计算逻辑都应该是相似的**。

1. **店主报任一端的缺陷,立案即自动附带另一端同病检查**(商家小程序↔网页端;顾客端有对应机制的一并查)——该缺陷的验收面包含**两端结论**,只给一端结论=没修完;
2. **同病在**:同批一起修,两端一起关单;
3. **同病不在**:必须回答"为什么两端不一样"——是因为共享同一后端/引擎所以另一端天然没有(好,写明共享点),还是两端各写了一份逻辑、恰好只有一份写错(坏,**登记为分叉债**,评估收敛为单一实现);"另一端没有这个页面/机制"也要明写,不许空着;
4. **计算逻辑两端必须同源**:金额、日界、门禁、状态机这类逻辑若发现两端各自实现,即使当下两边都"对",也算**底层分叉缺陷**单独立 D——收敛到单一实现(后端/共享模块),不许只修表象各修各的;
5. 反馈表按店主 08-12 规矩带**「端」列**,每条缺陷登记时写明发现端与另一端检查结论。

## 五、这套纪律的自评

每批交付末尾加一行自评：**"本批 L1–L5 各条是否都做到了？没做到的是哪条、为什么。"**
诚实写"L4 没做，因为演示数据里没有多技师单"，比写"全部通过"有价值得多——前者能让 Cowork 立刻补数据，后者是把雷留给店主开检时踩。

## 工具箱注记(S 组卫生批收档,2026-08-14)

- **删小程序源文件后必须整只重启 devtools**:编译缓存带鬼——症状=固定若干 walk 序列内 timeout、
  单跑全过、reLaunch 卡死白屏;文件恢复或整只重启即愈。删文件类改动的收工闸门前先重启。
- **弹窗 mock 只用 result 式**(`mockWxMethod('showModal', { confirm: true })`):函数式对 showModal
  不生效(真弹窗弹出无人可点);且不要连带 mock showToast(会毒化导航桥)。
- **codemod 幂等复跑=0 追加**记入方法库:机械批全类闭合的标准证据(Cowork 2026-08-14 认可)。
- **嵌套调用盲区**:整块括号配对式的 codemod/扫描器都会把嵌套在外层回调里的内层同名调用吞掉——
  步进必须 idx+1 而非跳到块尾(卫生批补账①实锤:60=57+3,其中 2 处漏挂)。
- **验尺独立原则(Cowork 2026-08-14 补,由上条升格)**:改码器与验证扫描器**不得共用同一套解析逻辑**——
  卫生批里两者同源,于是同一个嵌套盲区双双漏过,CI ⑳「0 容忍」形同虚设。凡机械批,验证器要么独立实现、
  要么至少用不同解析策略复检一遍(逐字符 vs 块配对);「施工尺和验收尺是同一把」=没有验收。
- **验尺独立原则(Cowork 升格,2026-08-14)**:凡机械批,验证器须独立实现或用不同解析策略复检——
  本次改码器与 CI 扫描器共用同一套括号配对解析,同一个嵌套盲区双双漏过,「0 容忍」形同虚设。
  **施工尺和验收尺是同一把=没有验收。**(行注释吃闭括号同坑已两次,第三次立独立条款。)
