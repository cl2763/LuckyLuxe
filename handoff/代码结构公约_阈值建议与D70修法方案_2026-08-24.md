**红线怎么用**(建议写法):超线文件**不许再加新功能**,只许改 bug 与拆分;拆完再加。
配套加一条常驻断言:扫这几个文件行数,超线且新增了函数 → 红。这样红线不靠自觉。

⚠️ **一个诚实的提醒**:`local-server.mjs` 从 18,929 拆到每个 ≤1,200,是 **~15 个模块**的工作量,
按公约②「边改边拆」大概要 10–15 个批次才能摊完。这期间它会一直超线 —— 所以红线对它的效力应当是
「**只许搬出、不许新增**」,而不是「立刻拆完」。要不要这么定,请你拍。

## 二、D70 修法方案(**等你批**)

### 前置:状态判定收敛成一处状态机

现状问题(查明报告已述):后端只白名单校验"值合法",不校验"从哪个态能去哪个态";
前端按钮各写各的(网页两颗裸按钮、小程序按 status 分支)。

**建议落法**:新模块 `apps/api/booking-state.mjs`(公约① 新功能新模块),里面只有一件事 —— **订单状态机**:

```
STATES        待付款 / 已确认 / 进行中 / 已完成 / 已取消 / 已过期 / 售后中
ACTIONS       确认到店 / 开始服务 / 完成 / 取消 / 标记爽约 / 转售后 / 售后结案
TRANSITIONS   每个动作:{ from: [...合法前置态], to: 目标态, guard: 额外前置(如"必须有已签署单"), effect: 副作用(入账/冲销/删占位) }
```

出口三个(**唯一实现**,双端与后端共用一套判定):
- `allowedActions(booking)` → 这单现在能做哪些动作(**按钮显隐从它推导,页面里不许再写 if 补按钮**);
- `assertTransition(booking, action)` → 后端 PATCH 前置校验(前端收敛了也挡直打接口);
- `applyTransition(booking, action, ctx)` → 执行状态变更 + 副作用(入账/冲销/占位)。

前端怎么用:后端在订单列表/详情的响应里下发 `allowedActions`(动作 key + 后端给的按钮文案),
**两端都只渲染这个数组** —— 与「后端出句」纪律同构,页面零判断、双端零分叉。

### 顺手拆:订单/售后域搬出巨型文件(公约②)

`local-server.mjs` 里与订单/售后相关的行约 **717 行**(含关键词行,实际连带更多)。建议搬出为:
- `apps/api/booking-state.mjs` —— 状态机(新写)
- `apps/api/booking-routes.mjs` —— `/admin/bookings/*` 与 `/my/bookings/*` 路由(搬)
- `apps/api/after-sales.mjs` —— 售后状态/事件/进度(搬,现有 `afterSalesState` / `afterSalesProgress` / `afterSalesProblem` 一族)

搬的纪律:**只搬不改**(先原样搬 + 跑全量回归绿),再在新模块里改行为 —— 两步分开提交,出问题好回滚。

### 三个待你拍的口径(查明报告里已列,这里给我的建议)

1. **两颗按钮的合法前置** —— 建议:「已完成」只在 `CONFIRMED / IN_PROGRESS`;「已取消」只在 `PENDING_PAYMENT / CONFIRMED`;
   已完成 / 已取消 / 售后单一律不出这两颗。
2. **全额到店单的入账时机**(最要紧,动财务口径) —— 三个选项:
   - **A**:入账随签署统一(全额到店单签署时也写账本)。**最干净**,但要处理存量 1035 单已按 `source='booking'` 入账的事实(不能重记,需迁移标记);
   - **B**:保留「已完成」入账,但把幂等改成「同一 booking 只要已有任何 income 行就不再记」。**改动最小**,风险最低;
   - **C**:两条都留,但在开单/签署时就把 status 置为 COMPLETED(现状部分单已经这样),让按钮彻底退出入账路径。
   我倾向 **B 先兜底(立即消除重复入账的口子)+ A 作为后续统一目标**。
3. **售后已完成的可见性** —— 网页补"售后处理详情"只读区(接口层 `/admin/bookings` 补 `afterSales` 字段 + 页面层详情面板加区块),口径与小程序一致。
