## 一、按店时区(B-1)

### 1.1 改法:一个默认值,带动 90 处调用点

以前 `localParts()` 里写死 `America/Toronto`,而全站 58 处 `localParts` + 32 处 `localDateTime`
都靠它算「今天 / 本月 / 日期分桶 / 营业时间判断 / 排班日视图 / 财务 occurred_on」。

没有去逐个改这 90 处,而是把**默认参数**改成「当前租户的门店时区」:

```js
function localParts(dateLike, tz = tenantTimezone()) { ... }
function localDateTime(date, time, tz = tenantTimezone()) { ... }
```

这些调用点全部跑在 `tenantContext` 里(请求进来时 `enterWith` 过),所以一次性全部租户化。
租户上下文之外的地方(启动、每日备份)拿到 `DEFAULT_TENANT_ID` → 与改造前完全一样。

### 1.2 新增的 helper 族

| 函数 | 作用 |
|---|---|
| `tenantTimezone(tenantId)` | 取本店主门店 `stores.timezone`;非法值或取不到 → 回落 `APP_TIMEZONE`。带缓存 |
| `invalidateTenantTimezone(tenantId)` | 门店时区一改立即失效(平台建店 + 门店 PUT 两处都挂了) |
| `localParts(dateLike, tz)` | 按指定时区拆出 `{date, time}` |
| `localDateTime(date, time, tz)` | 把「墙上时间」按门店时区换算成绝对时刻 |
| `todayOf(tenantId)` | 本店的今天 |
| `monthKeyOf(tenantId, date)` | 本店的月份键(财务分桶用) |
| `timeZoneOffsetMs(date, tz)` | 内部:某时刻在某时区的偏移,DST 也对 |

`localDateTime` 是这次唯一有实质算法变化的地方:以前是 `new Date('2026-08-08T21:30:00')`,
按**进程时区**解析;现在按门店时区把墙上时间换算成绝对时刻(先当 UTC 猜一次,再用落点自身的
偏移二次校正,跨 DST 边界也正确)。旗舰店门店时区 = 进程时区,所以它的结果与改造前完全一致。

### 1.3 新增只读接口 `GET /admin/store-clock`

```json
{"tenantId":"lucky-luxe","timezone":"America/Toronto","today":"2026-08-07",
 "monthKey":"2026-08","localTime":"04:22","serverProcessTimezone":"America/Toronto",
 "nowUtc":"2026-08-07T08:22:22.687Z"}
```

用来回答「服务端认为本店现在几号」。支持 `?at=<ISO>` 只影响这个回显,
让回归可以对**固定时刻**断言跨日/跨月边界,不依赖测试跑在一天中的哪个钟点。

### 1.4 关于指令里的「④ 提醒任务触发时刻按店时区换算」

查下来:现网所有 `reminder_tasks.scheduled_at` 都是 `addMinutes(new Date(), N)` 这类**绝对时刻**
(10 分钟后追问、草稿支付提醒、占位到期),不含任何墙上时间,本来就与时区无关 —— **没有可换算的东西**。
如实说明,没有编一条假断言。等价的真实风险是「当天时段窗口」(日视图 `dayStart/dayEnd` 由
`localDateTime(date,'00:00')` 算),已由 ④ 号断言覆盖。

## 二、七张子表补 tenant_id(B-5)

`payments` / `technician_schedules` / `business_hours` / `store_special_dates` /
`booking_slots` / `booking_status_history` / `booking_drafts`

两个刻意的设计选择:

**1. 加列不带 DEFAULT(可空)。** A-1 的教训就在这里 —— 带 `DEFAULT 'lucky-luxe'` 会让漏写的
INSERT 悄悄归到旗舰店名下,而代码里根本看不见那个租户 id。留 NULL 反而刺眼,回归直接断言「零 NULL」。

**2. 新写入靠数据库触发器从父表回填,而不是去改 13 个 INSERT 语句。** 改语句会漏、以后新增的
写入点也会忘;触发器是一次性的,对未来的写入同样生效:

```sql
CREATE TRIGGER payments_tenant_fill AFTER INSERT ON payments WHEN NEW.tenant_id IS NULL
BEGIN UPDATE payments SET tenant_id = COALESCE((SELECT b.tenant_id FROM bookings b WHERE b.id = NEW.booking_id), 'lucky-luxe') WHERE rowid = NEW.rowid; END;
```

存量按父表(booking / technician / store)回填;父表悬空的极少数行回落默认租户,
保证「零 NULL」这条纪律始终成立。**现有查询的父键条件一律未动 —— 行为零变化。**
