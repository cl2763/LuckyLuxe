# 可见档对照 · 店主记忆的开关 × staff_visibility 三档(2026-08-31j,只报不建)

## 1 找到了:店主说的那个开关

**业绩目标域的「显示」段选**(两端都有 UI,店主记忆无误):
- **网页**:员工管理 → 技师业绩 → 业绩目标,每技师一行两组段选 ——
  「设置:总目标/分项」+「**显示:仅总进度/含分项**」(admin.js 业绩目标面板);
- **小程序**:员工管理页 → 技师目标抽屉,同两组段选(staff/index.js sheet);
- **字段**:`perf_targets.display_mode`(`total_only` / `with_split`),**按技师×按月**存;
- **作用面**:员工端「我的业绩」页(双端同吃 staffPerformanceView)——
  `total_only` 时后端整页不下发分项字段(卡耗金额/单量目标,含每日流水行),前端自然无从渲染。
  面板底注原句:「显示=仅总进度时,员工端整页(含每日流水)不出现分项来源。」

## 2 对照表:两回事,不同轴不同粒度,有一块重叠的作用面

| | 店主记忆的开关(display_mode) | staff_visibility 三档 |
|---|---|---|
| 管什么 | 业绩页的**分项粒度**(看不看得到卡耗金额/单量目标) | 业绩、工资**两大块的有无**(perf_only/perf_and_salary/salary_only) |
| 粒度 | **按技师 × 按月**(perf_targets 行) | **按店**(tenant_settings 一枚) |
| UI | ✅ 两端都有(业绩目标面板/抽屉) | ❌ 零 UI(仅接口;全部店都在默认档 perf_and_salary) |
| 作用面 | staffPerformanceView 的分项字段裁剪 | ①同一 staffPerformanceView:salary_only 整块清空业绩;②salary/my-estimate:perf_only 403 |
| 重叠 | 同一页(员工「我的业绩」)被**两把刀各裁一维**:visibility 裁「块」,display_mode 裁「粒」 | 同左 |

**结论:两回事,不收敛** —— 一个管粒度(每人每月可不同),一个管板块(全店一刀)。
但同页双刀确实容易记混;若建 staff_visibility 的 UI,建议就放在**业绩目标面板同屏**
(店主记忆已经把它们归到一个地方),两把刀摆一起各标一句管什么。仍等小合同,我不动。

## 3 「非法值回落默认」静默失败器复查(一并报)

- **写口是终闸**:PUT `/admin/staff-visibility` 非法值 **400**(不落库)—— API 路径进不来坏值;
- **读口回落**只在一种情况命中:**库里被直写了三枚以外的值**(迁移事故/手改库)——
  此时 staffVisibilityOf 静默按 `perf_and_salary` 供数,**坏态被吞,没人知道**;
- 按静默失败器口径的判定:**不该 400**(读口炸掉=员工业绩页整页打死,可用性>洁癖,且写口已守),
  **但该留痕**。建议两选(等裁,未动):
  ① 命中即 `console.warn` 一行(坏值+租户)——最小改;
  ② 加一条库层判据进店群陪审团(逐店:staff_visibility 值 ∈ 三枚,坏值红)——
  与 I7「状态全在状态机集合内」同型,坏态升面见红,比 warn 更符合「判据也是代码」的家法。
